# 服务端能力缺口清单（面向文学发布平台 + Flutter 客户端）

本文回答一个问题：**除了"客户端要的接口有没有"之外，作为一个文学/长文发布平台，服务端还缺什么能力。**

如果说 [`client-coverage.md`](./client-coverage.md) 是"接口对不对得上"的逐条核对，本文是"这个平台还缺哪些功能"
的上位审视。判定依据是三份仓库内文档加上客户端的真实代码：

- `docs/requirements/behavior-baseline.md` —— 产品行为基线（公开内容 / 分类与标签 / 账号 / 社交 / 私信 / 通知 / 跨切面）。
- `docs/audit/feature-traceability.md` —— 逐能力"当前状态"表。
- `docs/roadmap/next-step-decision.md` —— 已审 7 个 issue 的处置结论（#58 / #61 / #63 / #64 / #66 / #71 / #72）。
- `BrainEno/flutter-blog`（`belog`）—— 客户端的 API 契约、页面清单与它自己写的"后端与客户端差距"一节。

图例：✅ 已有并且端到端可用 ｜ ⚠️ 有基础但闭环不完整 ｜ ❌ 尚未开发。

## 三、本次新增：关注流 `GET /api/v1/me/feed`

**为什么先做它。** 客户端已经有关注按钮和作者主页，`follow` 图谱、通知、粉丝/关注列表都齐了，但整条链路缺最后一环：
**关注之后，被关注者的新作品不会主动出现。** 没有这个能力，"关注"就只是一个计数器。

**行为变化：**

- 新增路由 `GET /api/v1/me/feed`（仅 GET，其他方法 405 + `allow: GET`）。
- 查询参数：`locale`（默认 `zh-CN`）、`limit`（1–100，默认 20）、`offset`（0–100000，默认 0）。
- 必须登录；匿名 → `401`。
- 返回**已发布**作品，按 `published_at DESC, id DESC` 跨所有被关注作者合并排序。
- 不返回草稿、不返回未关注作者的作品、不返回请求 locale 下没有译文的作品。
- 取关后立刻从 Feed 中消失；没关注任何人时返回空数组（**不是**公共 Feed）。
- 响应形状与 `GET /api/v1/articles`、`me/liked-articles` 完全一致（`serializeRestArticles`）。

**实现取舍：** 一次 `JOIN user_follows` 的 SQL 取页，而不是"按作者各查一页再内存合并"。
后者在作者发布频率不一致时，offset 分页会重复和丢条目。SQLite 与 PostgreSQL 两个适配器写同一条查询语义，
由 `persistence-adapter-contract.test.ts` 的共享契约（含排序、分页不重不漏、取关即消失、参数边界）同时约束。

**没有做的部分：** 客户端（Flutter）与 Web 前端目前都没有"关注"Tab，所以这一片**只有服务端**。
接口先落地，UI 由客户端接入时补——服务端不需要等客户端页面就能被验证。

## 三点五、本次新增：发现排序 `sort=latest` / `sort=popular`

**为什么是它。** `GET /api/v1/articles`（以及 `GET /api/v1/authors/:userId/articles`）此前只有一种顺序：发布时间倒序。
读者看到的是「最近」，不是「最近被读得最多的」——而后者才是新读者发现作品的入口。它是**已有列表能力的闭环**：
零 schema 变更，客户端首页只要多传一个参数。

**`popular` 的定义，以及为什么改成了全时段。** `sort=popular` 落地时是「最近 30 天发布的作品里按点赞数降序」。
**本次按 ADR 0016 决策 5 去掉了窗口**：`sort=popular` 现在 = **累计**收藏数降序，同分按发布时间降序。

- 这个栏目叫「最多收藏」，不是「本月热门」。两年前那篇高赞作品**就该**排在前面——它确实是本站被收藏得最多的作品之一。
  带窗口的排序会让「最多收藏」和「最新」只在变化速度上有区别，栏目之间就没有分工了。
- 去掉窗口也去掉了 `POPULAR_WINDOW_DAYS` 常量、`popularWindowSince()` 和两个适配器 SQL 里的一整段条件：
  少一个需要两边保持一致的常量，也少一处「到底是什么时候」的歧义。
- 只数**点赞**（= 收藏），不数评论：点赞是读者留下的最轻、最明确的信号；评论数会偏向争议性作品，在文学平台上未必等于质量。
  将来要加评论权重或时间衰减（HN 式）不需要改契约形状。
- 排序与 `query`、作者过滤**相乘而不是取代**它们：先过滤，再排序。
- `sort` 只接受 `latest` / `popular`，其它值 `400 BAD_INPUT`。

**取舍：** 没做时间衰减（HN 式 `score / (age + 2)^1.8`）。两个引擎的浮点与幂函数实现不同，
会让同一份共享契约在 SQLite 与 PostgreSQL 上产生细微不一致；整型的天窗口在两个引擎里都退化成一次时间比较，
行为可证明一致。

## 建议的下一步顺序

一眼看去缺口很多，排序原则只有一条：**先补"已有能力的闭环"，再补"全新的领域模型"。**
前者风险低、立刻产生用户价值；后者要动 schema、迁移和两个适配器，必须单独成片。

1. ✅ **关注流**（本次）—— `follow` 的闭环，纯查询，无 schema 变更。
2. ✅ **分类收紧为编辑专属** + ✅ **精选 `featured`** + ✅ **`most-saved` 改全时段** + ✅ **首页三个栏目** —— 后端与前端管理页都已完成；首页现在按「精选（编辑排的顺序）/ 最新 / 最多收藏（累计）」三段展示，编辑在 `/admin/featured` 随时调整。见第零节与 ADR 0016 决策 4、5。
3. **媒体库列表 + 孤儿回收（P4）** —— 与作者日常强相关，且 P4 已被独立标记为待决策。
4. **举报 / 审核 / 角色** —— issue #72，先写 ADR 再动代码。
5. **会话管理 + 注销账号** —— 账号安全 G2 的收尾。
6. **OpenAPI 契约** —— issue #63，客户端接入越多收益越大。

## 与客户端的关系（截至本次）

- 客户端（`belog`）尚未接入关注流，也没有"关注"Tab —— 服务端先行，客户端接入时补 UI。
- 客户端的 Markdown → `contentBlocks` codec 仍是 **v0**（段落 / 图片），会把标题、引用、列表压平成段落。
  服务端早已支持 v1 富文本，这是**客户端**侧的缺口，不是服务端缺口。
- 客户端"账号安全 G2"里记录的缺口（忘记密码 / 重置 / 邮箱验证 / 改邮箱 / 登录态改密码），服务端**已全部具备**，
  差的是客户端 UI。
