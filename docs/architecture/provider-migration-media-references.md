# Media references in provider replay

## Status and limits

This is an incremental replay safeguard, **not a provider-cutover protocol**. Do not use it for a production migration or enable target media deletion while a target is catching up. [ADR 0010](decisions/0010-sqlite-first-and-online-provider-cutover.md) still requires a consistent initial snapshot, an agreed journal watermark, reconciliation, writer fencing, cutover and rollback. None is provided here. Identity-token and other replay gaps also remain ([#218](https://github.com/BrainEno/no-wave/issues/218)).

The replayers currently support media replay **only from an empty media baseline**. On preparation and again in the first target apply transaction, they reject a target containing any `media_assets`, `article_media_refs` or `article_translations`, or profiles with `avatar_media_id` or a media-path `avatar_url`. This deliberately rejects even a seemingly consistent pre-existing snapshot: neither its provenance nor its watermark can be established by this code. Other target data, such as pre-seeded owner accounts, is not thereby certified. The check is not a writer fence, and a successful check does not prove that a complete source snapshot was copied.

Replay requires the exact wire-contract version exported as `MIGRATION_REPLAY_SCHEMA_VERSION`. Sessions with earlier or unknown versions are rejected, including sessions whose target checkpoint has already passed old translation events. Do not relabel an old session or start a new session on an old target to bypass this guard. Without coordinated rebuilding and reconciliation, old targets, backfills and old journal tails cannot be trusted. There is no implemented repair, snapshot importer or production runbook in this change; [#217](https://github.com/BrainEno/no-wave/issues/217) remains open for those gates. Do not delete or rebuild any production data based on this document.

## Incremental contract

- After creating or editing a translation, each source store reads the actual `article_media_refs` rows for that article and locale inside the same transaction. The translation journal payload includes the complete set of asset IDs, including an explicit empty set. It is derived from the materialized source rows, not guessed from a URL or the replay target.
- This set is journal-only metadata. The target validates it, rejects missing, malformed or duplicate IDs, validates the translation's composite key, and never treats metadata as an SQL identifier. Translation snapshots lacking the set fail closed. Older appliers reject the new metadata rather than applying a partial row. All source writers must still be version-matched; rolling upgrades are not a fencing protocol.
- The target upserts the translation, replaces **only that locale's** references, and records the apply ledger and checkpoint in one transaction. Each captured ID is inserted under the existing foreign keys; a missing asset aborts the transaction rather than being silently omitted. Every apply checks that SQLite foreign keys are enabled or that PostgreSQL is not in replica mode (which disables ordinary FK triggers), including after a checkpoint has advanced. This assumes the migrated constraints and triggers themselves have not been removed or individually disabled. Duplicate replay does not restore a stale set or rewind a checkpoint. Out-of-order source transactions are rejected.
- Tombstones and restoration keep references; an article hard delete cascades them. A translation delete also removes that locale's reference set. Adding/removing an image in one locale does not affect another locale.
- Profile snapshots must explicitly include `role`, `avatar_url` and nullable `avatar_media_id`. The target preserves those values and the avatar's existing `ON DELETE RESTRICT` foreign key. A snapshot without them is rejected rather than silently dropping an avatar or defaulting a role. This narrowly addresses profile media replay; it does not resolve the remaining identity/account, token or featured-shelf gaps in #218.
- Asset rows remain owner-scoped and preserve their original IDs, owner, storage key and metadata. The change neither copies image bytes nor relaxes access checks or foreign keys. The journal already contains article and identity data and remains sensitive; restrict access, logging and retention as required by ADR 0010.

Only instrumented store writes participate. Direct SQL, older writers and other uninstrumented paths can bypass capture; this safeguard cannot establish source integrity or repair a source that already has incorrect materialized references. The target must remain isolated from unrelated writers. In particular, if a target-side delete commits **before** an as-yet-unapplied article reference, the subsequent replay fails its foreign key and leaves its checkpoint unchanged, but that cannot undo an already deleted media object. A successful replay of some batches is therefore not authority to delete object bytes or promote the target.

Real SQLite ↔ PostgreSQL tests exercise new sessions, edits and locales, drafts, tombstones, restoration, hard-delete cascade, avatars, roles, missing dependencies, transaction rollback, stale sessions and baselines, duplicates, ordering, concurrent source edits and both commit orders of target replay versus deletion. They do not prove snapshot consistency, a source/target watermark, production-scale reconciliation or an operational cutover.
