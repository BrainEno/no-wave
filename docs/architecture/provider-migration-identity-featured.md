# Identity and featured-shelf snapshots in provider replay

## Scope and hard limits

This is an incremental capture/replay contract, **not a production provider-cutover protocol**. [ADR 0010](decisions/0010-sqlite-first-and-online-provider-cutover.md) and [#217](https://github.com/BrainEno/no-wave/issues/217) still require a consistent initial snapshot, a matching journal watermark, complete source-write coverage, reconciliation, writer fencing, cutover and rollback. None is implemented here. Migrating media object bytes is separate. Do not promote a target or delete/rebuild production data based on these tests.

The current replayers require the exact `MIGRATION_REPLAY_SCHEMA_VERSION` (`media-identity-snapshots-v2`). Earlier or unknown sessions are rejected even if they already have a checkpoint: old token replacements may have lacked their deletions and old media snapshots may have lacked references. Never relabel an old session or attach it to an old target to bypass this check.

Preparation and the first target apply reject pre-existing sessions, access/refresh/identity-token rows, revocations and rate-limit rows. The media baseline also rejects featured-shelf rows. This is a conservative **partial** baseline check, not an attestation of either database: it does **not** check or authenticate pre-existing target accounts, password hashes, email verification state, profiles or roles, and it does not prove that pre-existing source rows were captured. Tests that seed an identical account on both databases are fixtures, not a backfill protocol. A target must remain isolated from unrelated writers; checking once is not continuous fencing. Neither an empty target nor a successful replay proves that the source snapshot, identities or privileges are complete or correct. Do not use this path to migrate existing users without the missing coordinated snapshot and reconciliation.

## Incremental identity contract

- Account snapshots include the actual nullable `email_verified_at`; session, access, refresh, rate-limit, revocation and identity-token snapshots carry their complete security-sensitive fields. Explicit nullable fields cannot be omitted or replaced by defaults. Replay rejects unknown columns, malformed digests, unsupported token purposes, invalid timestamps and invalid counters. Database foreign keys, uniqueness and other constraints still apply. A rejected transaction leaves the target checkpoint and all of its rows unchanged.
- Issuing a token replaces the previous rows for that account and purpose. The source records a delete for every replaced digest and an upsert for the new row in the same transaction. PostgreSQL locks the account before checking its address and replacing tokens, including when the prior set is empty; SQLite uses its serialized write transaction. Consumption records the consumed row; expiration pruning records deletes. Duplicate replay cannot rewind the checkpoint or revive an already-applied earlier snapshot.
- Changing an account's address invalidates all its existing verification and recovery tokens in the same source transaction, and captures their deletions with the account update. Issuance refuses a stale address. Recovery and verification must pass the consumed digest to their final credential/verification write; that write checks, under the same transaction and account lock, that the proof remains present, consumed, belongs to the account, has the correct purpose and still names the current address. A refusal neither changes the credential nor revokes sessions. This also covers the address changing away and back while an operation is in flight. Source behavior changes only after the new code is actually deployed; this branch alone provides no production mitigation. Existing token rows are not retroactively certified or removed by this change; any production cleanup or invalidation requires explicit operator review and approval.
- Password replacement and session revocation are captured together, as are the resulting access-token revocations and refresh-token states. PostgreSQL takes the account lock before session locks so recovery and ordinary password changes use the same order. Role changes are captured as complete profile snapshots; an already-applied earlier promotion cannot overwrite a later demotion on duplicate replay.

## Featured shelf

`featured_articles` is an ordered list, not an unordered collection. Replacement captures deletes for the old shelf and complete rows for the new shelf in one source transaction; the target applies the transaction and checkpoint atomically. PostgreSQL serializes whole-shelf replacements with a schema-scoped transaction advisory lock, including replacements of an empty shelf; SQLite serializes writers. Unauthorized edits, duplicates, excessive lists and non-published works remain rejected by the existing store contract. Soft-deleted articles retain their shelf rows but are hidden by the published read; a hard delete cascades the row.

## Auditing and sensitive data

A real-database test compares the 24 literal entity types captured in each source store with the replay allowlist and both migrated schemas' columns, primary-key columns, foreign-key column pairs/delete actions and unique-index columns/partial flags. It does not prove equivalence of every CHECK expression, partial-index predicate or future/dynamic write path, nor verify that deployed constraints have not been disabled or altered. The change-specific tests exercise uniqueness, foreign keys, rollback, retry and checkpoint behavior in both directions, as well as controlled source races. Direct SQL, old binaries and other uninstrumented writers can bypass capture.

The journal can contain email addresses, salted password hashes, token digests, access-token identifiers, rate-limit keys and other private data. These are sensitive even though plaintext passwords and raw verification, recovery and refresh tokens must never be journaled. Restrict database, backup and log access; minimize retention; never log raw tokens, token-bearing links or whole migration payloads. Review the security and retention policy before enabling capture in any real environment.
