# ADR 0043: 告警交接使用签名离线批次、独立持久收件箱和显式结算

- Status: Proposed
- Date: 2026-11-12
- Implementation: Partial — 仓库内有限离线命令、独立进程与故障演练已实现；生产接线与外部通知渠道未启用。
- Scope: #331 的告警事件交接切片；不替代 ADR 0042 的观测规则，不完成整个 Phase 6。

## 背景

[ADR 0042](0042-finite-read-only-operational-monitor.md) 已将告警事件持久化到
monitor 日志，直到消费者显式确认。成功打印 stdout、复制文件或 HTTP 202 都不能
证明消费者已可靠接收；来源确认和下游处理也不是同一个动作。我们需要可独立验证、
不借用业务数据库权限的仓库内交接实现，但尚未批准外部告警账号、网络接收器或部署。

## 决策

1. **传输与接收分离。** 新增默认不运行的 `ops:handoff` 有限命令；只读取显式
   文件，不联网、不加载 `.env`、不启动 API/worker、不连接业务 store、不安装定时器。
   操作者负责在可信通道中转交事件包和回执；本轮不自动复制跨主机文件或发送 webhook。
2. **双方独立 Ed25519 身份。** sender 只持来源私钥和 receiver 公钥；inbox 只持
   接收方私钥和明确来源公钥 allowlist。配置拒绝未知字段、非 canonical DER/base64、
   非 Ed25519、重复身份/公钥和双方共用签名 key。消息签名包含角色分离的 domain，
   严格重建固定字段顺序，不信任产物自带的公钥或未经独立核验的 verifier profile。
3. **一个来源只能有一个在途意图。** `prepare` 先持久化完整 monitor 未确认队列，
   再以 create-only 原子发布事件包。批次携带 stream/receiver、递增 sequence、
   前一 batch ID、原 monitor 配置指纹、事件事实及准备时间。重试返回原批次；
   后续 monitor 事件可以追加，但不能替换正在交接的前缀或重置链。
4. **先入箱，再签发可恢复回执。** `receive` 验证签名、事件 ID/时间/转换连续性、
   sequence 与前驱后，在同一私有本地 journal 中提交事件和签名回执，再发布回执文件。
   相同最新批次只重发相同回执，不重新入箱；更旧批次和同序号 fork 失败关闭。
   每来源持久保留一个最新 receipt/cursor；已消费事件也不会让旧批次重新获得写入资格。
5. **结算是显式授权，不是副作用。** `settle` 先验证与在途批次完全匹配的回执，
   提交 receipt intent，再在 monitor 自有锁内核验完整原事件前缀并确认，最后完成
   sender 链。若确认后最终提交中断，只有匹配的 acknowledged-through、非倒退 revision
   与观测时间才能完成重试；新追加事件不受影响。没有回执时不确认 monitor。
6. **接收与消费是两种证明。** 独立 inbox 需要下游可靠处理后才显式 `consume` 一个
   实际存在的精确前缀；它不改变 monitor、告警条件或接收回执。`receipt` 只恢复
   指定来源最近一份已持久化回执，不凭队列为空重建历史回执。
7. **只读核验不能生成新进展。** 分页 cursor 签名并绑定确切 inbox 快照；改变
   revision/内容后旧 cursor 失效。status 区分事件年龄、接收年龄和等待预算，绝不刷新
   时间。`reconcile` 只比较多个独立快照，明示不是分布式原子快照，也不自动修复。
   `profile` 只导出双方公钥 pin；`verify` 可在没有任何私钥的工作站核验历史证据，
   保留全部年龄及缺少 receipt 的事实。命令成功不代表服务健康或人员收到通知。
8. **复用私有文件边界。** 从 monitor 抽取既有 POSIX journal/有界输出原语，保留
   owned regular file、0700 父目录、0600 新文件、inode 锁、外部改写检测、原子 rename
   与 fsync。新产物用同目录临时文件和 no-replace link 发布；同字节重试重新 fsync，
   不覆盖不同文件。搬移与薄适配不计入本轮新增功能行。

## 容量与操作前提

- 一个 batch 包含整个 monitor 队列，1–256 个事件、最多 16 个目标、最多 256 KiB。
  不切开一次 evaluation 的事件，下一批必须来自更晚的 monitor revision。
- 一个 inbox 配置 1–16 个固定来源，全局最多 1024 条未消费事件；状态最多 2 MiB，
  配置最多 16 KiB。满额保留旧状态，拒绝接收新批次，不自动删事件、回执或“过期”锁。
- 需要受控本地 POSIX 持久盘、同步的跨主机时钟和明确的单来源写权。网络文件系统、
  Windows ACL、源/接收日志回滚与主机持久性仍须单独资格验证。
- 配置指纹绑定公钥与身份，sender 另绑定原 monitor 的绝对配置/状态路径。不提供
  强制重绑定、自动 key rotation 或清空日志。变更身份、恢复旧备份必须先停止参与者，
  由 owner 对所有在途事件、回执、消费状态及旧链逐项核对；不要删除旧状态来绕过校验。

## 不选择的方案

- 看到 stdout 成功或复制成功就自动 ack：缺少消费者持久接收证明。
- 将告警接到业务 outbox/Notion job：扩大业务数据权限，混淆通知故障与告警交付故障。
- 使用一个共享 HMAC key 让双方都能签回执：不能提供独立角色的签名边界。
- 自动发送外部 webhook、SMTP、聊天渠道或安装常驻 receiver：目的地、凭据、重试、
  服务生命周期和实际通知验收尚未获得独立批准。
- 无限保存 event tombstone：改用严格批次链和有限每来源 cursor，满 inbox 失败关闭。
- 自动回退/抢锁/恢复备份：不能证明旧进程和旧写权已停止，也不能保证没有丢失未交付事件。

## 剩余门禁

这是一条有边界的本地持久交接协议，不是 HA 告警服务、人员呼叫平台或生产放行。
Ed25519 验证的是被信任 key 签过的内容，不是硬件磁盘永不丢失的证明；本地 journal
也没有防同 UID 恶意改写的签名/MAC。删除或恢复旧 journal 可能破坏去重和回执保留。

真实宿主机 fsync/崩溃锁、存储丢失/备份恢复、跨主机安全文件传输、外部通知渠道、
监控自身失联、时钟运维、密钥轮换/交接和人员响应仍开放。没有部署、业务数据库写入、
通知重投、Notion replay 或 moderation 扩权。详见[操作规程](../../operations/alert-handoff.md)。
